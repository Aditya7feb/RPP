# TLS Connection Schema

**File:** `schemas/tls-connection.md`

**Version:** 1.0.0

---

# Purpose

The TLS Connection Schema defines the canonical representation of one TLS transport lifecycle.

A TLS Connection links the handshake, session, certificate chain, validation result, and evidence generated by the TLS Client.

---

# Design Principles

A TLS Connection SHALL be

- Traceable
- Lifecycle aware
- Evidence backed
- Adapter independent
- Assessment scoped
- Safe to reference
- Explicit about state

---

# Identity

Every TLS Connection SHALL contain

```yaml
connection_id:

schema_version:
```

Connection IDs SHALL be unique within an assessment.

`schema_version` SHALL be `1.0.0`.

---

# Assessment Relationship

Every TLS Connection SHALL contain

```yaml
assessment_id:

task_id:

request_id:
```

`assessment_id` identifies the owning assessment.

`task_id` identifies the task that authorized the connection.

`request_id` identifies the interface request.

---

# Target

Every TLS Connection SHALL contain

```yaml
target_host:

target_port:

transport_protocol:
```

`target_host` SHALL be the DNS hostname or IP literal actually connected to.

`target_port` SHALL be an integer from 1 through 65535.

`transport_protocol` SHALL be `tcp` or `udp`.

`udp` SHALL require an explicitly enabled DTLS adapter.

---

# Lifecycle State

Every TLS Connection SHALL contain

```yaml
state:

opened_at:
```

Allowed states

```
opening

open

closing

closed

failed
```

`opened_at` SHALL be an RFC 3339 UTC timestamp.

---

# Closure Metadata

TLS Connections MAY contain

```yaml
closed_at:
```

`closed_at` SHALL be an RFC 3339 UTC timestamp on or after `opened_at`.

`closed_at` SHALL be present when `state` is `closed` or `failed`.

---

# Related TLS Objects

TLS Connections MAY contain

```yaml
handshake_id:

session_id:

certificate_chain_id:

validation_id:
```

`handshake_id` SHALL reference a TLS Handshake and SHALL be present when `state` is `open` or `closed` after handshake completion.

`session_id` SHALL reference a TLS Session when session metadata exists.

`certificate_chain_id` SHALL reference a Certificate Chain when the peer supplied certificates.

`validation_id` SHALL reference a TLS Validation Result after validation starts.

---

# Evidence

Every TLS Connection SHALL contain

```yaml
evidence:
```

Evidence SHALL be an array of Evidence IDs conforming to `schemas/evidence.md`.

Evidence MAY be empty only before collection.

---

# Extensions

TLS Connections MAY contain

```yaml
extensions:
```

Extensions SHALL contain namespaced adapter metadata.

Extensions SHALL NOT contain secrets.

---

# Example

```yaml
connection_id: tlsconn-01
schema_version: 1.0.0
assessment_id: assessment-2026-001
task_id: task-042
request_id: req-7a8d
target_host: api.example.com
target_port: 443
transport_protocol: tcp
state: open
opened_at: '2026-07-25T10:00:00Z'
handshake_id: tlshs-01
session_id: tlssession-01
certificate_chain_id: tlschain-01
validation_id: tlsval-01
evidence:
  - evidence-tls-01
```

---

# Validation Rules

A valid TLS Connection object SHALL contain

- Connection ID
- Schema Version
- Assessment ID
- Task ID
- Request ID
- Target Host
- Target Port
- Transport Protocol
- State
- Open Timestamp
- Evidence References

---

# Success Criteria

A compliant TLS Connection object provides a complete lifecycle record for one TLS transport.

It enables platform components to trace TLS activity from request through handshake, validation, evidence, and cleanup.
